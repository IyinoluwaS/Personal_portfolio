Ledger Agent

A natural-language-to-SQL agent for a personal finance ledger. It checks its own queries, repairs them from the exact error and refuses rather than guess. I built it to measure how much a self-repair loop is actually worth.

My role
Everything: design, build and evaluation
Type
Personal project
When

Stack

01 — Problem

A wrong number is worse than no answer

Text-to-SQL demos often look right and return the wrong figure. For a question like “How much did I spend on groceries in March?”, a confident wrong answer does more harm than a refusal.

I wanted an agent that either returns a number it can back up or says it can’t answer. I also wanted evidence, not a hunch, about whether its self-repair loop helps.

Who it’s for

Someone asking questions about their own spending. It’s a learning project: the ledger is synthetic and seeded, so anyone who clones the repo gets identical data and comparable results.

02 — What I built

My contribution

My work: a solo project

  • A LangGraph state machine with five steps, only two of which call the model
  • A deterministic SQL guard that validates every query against the live schema
  • A read-only data layer: nothing outside one module touches the database
  • A seeded synthetic ledger that models monthly bills separately from everyday spending
  • An evaluation harness: 16 questions with hand-written ground truth, run under four conditions

03 — How it works

Two model calls, three deterministic checks

ModelDeterministic code

  1. Load schemaCodeReads tables, columns and three sample rows per table from SQLite. This is all the model learns about the data.
  2. Write SQLModelWrites one SELECT. On a retry it also gets the failed query and the exact error.
  3. GuardCodeRejects anything that isn’t a single SELECT, has no LIMIT, or names a column that doesn’t exist.
  4. ExecuteCodeRuns on a read-only connection and returns rows or an error as a value. It never raises.
  5. ExplainModelTurns rows into an English answer, or an honest “I couldn’t answer that.”

If the guard or SQLite rejects a query, the error message goes back to step 2, up to a configurable retry budget. The model doesn’t get smarter on the second attempt; it gets better information, such as column 'merchant' does not exist. Available: id, merchant_id, …

04 — Decisions

Choices and their trade-offs

Errors are values, not exceptions

The query runner returns (rows, error) instead of raising. You can’t route a graph on an exception, but you can route on a value, and that single choice is what makes the repair loop possible.

Two independent safety layers

The database connection is opened read-only, so SQLite itself refuses writes, and the guard rejects anything that isn’t one SELECT. The prompt also asks for safe SQL, but I treat that as a hint. A prompt is not a security boundary.

Money stored as integer cents

Floating-point error accumulates across thousands of rows, so all arithmetic happens in cents and the division by 100 happens once, at display time.

A pattern-based guard instead of a SQL parser

The guard is short, transparent and fast, with no extra dependency.

Trade-off: it has known blind spots, such as SQL comments and LIMIT inside a string literal. I chose to document those rather than write a full parser; they’re listed under limitations below.

05 — The hard part

The bugs were in my measuring tools

Problem
Some early failures looked like model mistakes. A question that should take one attempt was taking two, because the guard rejected SUM(amount_cents) AS total_cents: total_cents isn’t a real column, but it is a legal alias.
What I tried
My first fix stripped the AS definition before checking identifiers. That was incomplete: the alias is also referenced later, in ORDER BY, and that reference was still rejected.
Fix
Collect every alias a query defines into an allowed set before checking identifiers. Reading the ablation failures, not just the score, also turned up two grading bugs: a month written as “March” when the data stores 2026-03, and an empty aggregate returning one row of NULL rather than zero rows.
Result
Each bug became a test case. I fixed the ground truth instead of loosening the grader, because a fuzzy grader would also accept wrong answers.

06 — Testing & reliability

How I know it works, and how it fails

Evaluation

16 questions across easy, medium and hard tiers. I wrote every answer in SQL by hand before the agent saw the question, then cross-checked the answers against each other: the three monthly totals sum exactly to the grand total. Answers are graded on returned values, never on query text, because many correct queries exist for one question. A missing ground truth counts as a failure, and each ablation changes exactly one variable.

Unit tests

The guard ships with 13 self-tests covering rejected writes, stacked statements, missing limits and invented tables or columns. All 13 pass.

Failure handling

An empty result means “no rows matched,” never an invented figure. An exhausted retry budget returns “I could not answer that” with the last error. The model is pinned to a dated snapshot so the four runs compare like with like.

The rich prompt spells out what this model tends to get wrong: money is in cents, dates are text, SQLite has no DATE_TRUNC. With those hints, first attempts are almost always right. Strip the prompt back and first-attempt accuracy falls to 62%; the repair loop brings it back to 94%.

My conclusion: the repair loop and prompt engineering are substitutes. The loop delivers the same constraints as error messages, only for the queries that need them. It restores correctness, not quality: a twice-rejected model writes a right but noticeably clumsier query.

Known limitations

  • Results come from 16 questions on synthetic data, not real users or real bank data
  • SQL comments aren’t stripped before scanning, and LIMIT inside a string literal satisfies the limit check
  • Escaped apostrophes, such as 'Trader Joe''s', can cause false rejections
  • Foreign keys are declared but not enforced

Next steps

  • Guard against prompt injection through sample rows: a merchant name containing instructions reaches the model via the schema
  • Estimate query cost before running it, since a LIMIT doesn’t prevent an expensive scan
  • Add a human approval step before execution, and use a cheaper model for the explanation step
